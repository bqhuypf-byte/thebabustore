# Website feature audit

Inspect the actual website in a browser and produce a project-local Markdown specification that another developer can use to reproduce its observed behavior. Follow the user's stated scope, destination, and permissions. If no destination is given, write `website-feature-audit.md` at the project root; preserve existing files and choose a non-conflicting name when appropriate.

## Workflow

1. Identify the source URL, relevant public and authenticated areas, and the project context. Use a connected browser or service connector when available. Sign in only with credentials or an existing session the user has authorized; never include passwords, cookies, tokens, private customer details, or sensitive production data in the report or version control.
2. Build a coverage inventory from visible navigation, page links, user-provided paths, and observed flows. Visit each in-scope page, recording its actual URL, role, key sections, responsive layout, typography, imagery, and relevant visible states. Include admin sections when in scope. Record representative screenshots only if useful and allowed; do not invent asset details.
3. Exercise interactive, non-destructive behavior: navigation, hover/focus states, menus, search, filters, tabs, modals, image galleries, validation, and cart interactions when permitted. For checkout or other workflows inspect steps up to submission and document consequences. Never complete a purchase, transfer funds, submit a real order, message others, delete records, or change production data unless specifically authorized for that operation. When safe test records or a sandbox are available and authorized, use them; record exactly what was tested and any cleanup performed. Respect site access controls and do not bypass CAPTCHAs or security barriers.
   When evaluating an implementation, also check for visible and functional bugs, not just whether a control appears: inspect desktop and mobile layouts, modal contents and scroll behavior, oversized images, clipped controls, overflow, missing assets, broken links, console/network failures, validation and failed actions. Reproduce failures with steps, expected and actual results, URL and viewport; distinguish confirmed defects from untested cases. After a requested fix, rerun the affected flow and inspect it visually before reporting success.
4. Document each flow as entry point → user action → visible result, including required fields, states, navigation, errors, and relevant dependencies between storefront and admin. Distinguish observed behavior from inference, code evidence, assumptions, and untested claims. Cite concrete URLs and UI labels; avoid copying private data. Record unreachable pages, inaccessible roles, untested destructive operations, and any discrepancies or uncertainty explicitly. Never claim exhaustive coverage if any workflow or page was not inspected.
5. Write the Markdown report with a concise scope and date, a coverage/status inventory, page-by-page structure, interaction and workflow specifications, admin/storefront data relationships, responsive/design notes, and remaining unknowns. Structure it around evidence, not filler. Include implementation implications where relevant but do not modify the project application unless requested.
6. Reopen the output and check that links, paths, coverage labels, and sensitive-data handling are accurate. Report the file location and the principal coverage limitations. Do not store credentials or authentication state in the skill or the report.
